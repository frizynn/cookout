# Null is allowed, because the protocol uses it

2026-11-22 (mattpocock/cookout#27, extending [ADR 0012](0012-lint-opt-outs.md)). A chief-of-staff choice, pending Matt's review. `unicorn/no-null` is off everywhere. The wire protocol needs `null`: a top-level message's `latestReplyId` is `null` until it has a reply, and a message's `data` is any JSON value, `null` included, which must stay apart from no data at all. SQLite needs it too, since `node:sqlite` binds `null` as SQL `NULL` and rejects `undefined`. No code can write those values with the rule on except by building `null` some other way, such as `Option.getOrNull(Option.none())`. That only hides the literal from the rule, and it would be copied. Turning the rule off only where the protocol needs `null` doesn't give a clean scope, because the messages module, storage, the SDK's tests and the storage tests all need it. Code that means "nothing here" still uses `undefined` or `Option`. That choice is for `eslint(no-undefined)` and code review to police, not this rule.
