# Nudges are scheduled from storage, on fixed intervals for now

2026-11-23 (mattpocock/cookout#221, spec #215). A **Nudge** is a reminder in the Inbox that an open thread has been quiet for a while (Matt, 2026-11-23, on #215 and #221). The starter of an open thread gets the first nudge 3 days after the thread's last activity (its latest message, or its last reopen if later, as Open threads defines it) and a second 7 days after the first, then none until new activity. Matt decided on #215 (2026-11-23) that threads quiet since before nudges shipped get none, that a reopen restarts the quiet clock, and that `cookout watch --until-mention` stops at a nudge.

## Decision

- **Storage is the only truth.** Each nudge is a record (both Layers, a migration, the contract suite): its ID, thread, recipient, which nudge it is, when it was raised and whether its recipient marked it read. When the next nudge falls due is never kept anywhere else: storage answers it from the open threads and each thread's newest nudge.
- **One fiber in the nudges Layer's scope** asks storage for the next due moment, sleeps on Effect's Clock until then, has storage raise every nudge due by now in one operation (recorded before its `nudge` event is sent), and asks again. A new message, a close or a reopen wakes it early, since each can move the next due moment. A restart therefore neither loses nor repeats a nudge, and one that fell due while the server was down is raised at boot, once.
- **The precedents.** The server already does timed work two ways. Presence's 60 s grace and 5 min boot grace ([ADR "presence comes from live connections"](0056-presence-comes-from-live-connections.md)) fork an `Effect.sleep` into the presence Layer's scope and keep the state in memory, which suits seconds and minutes. Webhook retries keep `nextAttemptAt` in storage and resume each pending delivery at boot. Nudges wait days, across deploys, so they follow the webhook retries: the schedule comes from storage, and the sleep is only a wait for the next look. Both run on Effect's Clock, so tests drive them with `TestClock` and the test cookout's restart.
- **Read is derived as well as stored.** A nudge is unread only while its recipient hasn't marked it read (one at a time, or with Mark all as read up to the newest nudge seen), its thread is still open and nothing has happened in the thread since it was raised. So a reply or a close reads it in the same change that stores them, and a later reopen doesn't make it unread again.
- **The recipient** is the top-level message's author, worked out when the nudge is raised: a Deactivated agent's owner instead, and nobody when that owner, or a human author, is Deactivated. A nudge for nobody is still recorded, so the thread's clock moves on as for anyone else.
- **Before nudges.** The store records when it began raising nudges (SQLite fills `nudges_since` on its first open after the migration); a thread whose last activity is older gets none until new activity.
- **Fixed intervals for now.** The 3 and 7 days are constants in one place, `nudgeIntervals` in the inbox module, which also spells the two texts. Storage takes them as an argument, so making them a board setting (#211) changes only where they come from.
- **On the wire.** `GET /v1/inbox` and the inbox history carry `nudges` next to `items`, as offline alerts carry `alerts` (#185): unread nudges in the inbox, all of them on the history's newest page. `POST /v1/inbox/nudges/:id/read` marks one read, and `POST /v1/inbox/ack-all` takes `nudgesUpTo`. The `nudge` event goes to every live stream of the recipient and has no SSE `id`, since the stream's IDs are message IDs.

## Considered options

- **A sleeping fiber per thread, in memory, as presence's grace does.** Rejected: a deploy would forget every pending nudge, and a restart would have to rebuild them all anyway.
- **A periodic sweep (every hour, say).** Rejected: nudges would come up to an hour late, tests would have to step the clock, and the sweep would run when nothing is due.
- **Store the next due moment on each thread.** Rejected: every message, close and reopen would have to update it, in both Layers, and it can drift from the rule it caches.
